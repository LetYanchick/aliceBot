# Улучшения алгоритма бота

## Анализ исходного алгоритма

Алгоритм Алисы прост и предсказуем: тратить ровно половину еды на исследование, двигаясь к ближайшей непосещённой комнате с наименьшим номером, собирая только один лучший ресурс. Это создаёт ряд неэффективностей.

---

## Улучшение 1: Жадный выбор маршрута по ценности ресурсов

**Проблема исходного алгоритма:**  
Бот всегда идёт к непосещённой комнате с наименьшим номером, не учитывая, какие ресурсы там лежат. Это приводит к тому, что он может потратить всю исследовательскую еду на комнаты с exp (ценность 1), проигнорировав рядом стоящую комнату с gems (ценность 46).

**Предложение:**  
На каждом шаге исследования выбирать следующую комнату не по наименьшему номеру, а по максимальной ожидаемой ценности ресурсов. Для видимых комнат (смежных с посещёнными) ресурсы неизвестны, но можно использовать статистику уже посещённых комнат для оценки.

**Реализация:**  
```
score(room) = known_value(room) / cost_to_reach(room)
```
Для неизвестных комнат можно использовать среднюю ценность по уже посещённым.

**Плюсы:**
- Значительный прирост ценности при неравномерном распределении ресурсов
- Особенно эффективно при небольшом запасе еды

**Минусы:**
- Усложняет код
- Может хуже исследовать граф — часть комнат останется непосещённой

**Когда хуже:** Если ресурсы распределены равномерно и важно исследовать как можно больше комнат — жадный выбор не даёт преимущества.

## Улучшение 2: Динамический бюджет еды вместо жёсткого деления 50/50

**Проблема исходного алгоритма:**  
Бот всегда тратит ровно `M/2` на исследование. Это приводит к двум крайностям:
- При M=4 бот исследует только 2 комнаты, хотя мог бы исследовать 3 и безопасно вернуться
- При M=100 бот исследует 50 шагов, но граф может оказаться маленьким — еда теряется впустую

**Предложение:**  
Перед каждым шагом исследования динамически проверять: `food_remaining - cost_to_next - cost_to_return_from_next >= 0`. Идти только если хватает еды на возврат. Исследование продолжается максимально долго, пока позволяет еда.

```cpp
int returnCost = bfs_distance(current, 0);  // реальное расстояние до дома
int moveCost = cost_to_reach(nextRoom);
int returnFromNext = bfs_distance(nextRoom, 0);  // после перехода

if (food - moveCost - returnFromNext >= 0) { go(nextRoom); }
```

**Плюсы:**
- Использует доступную еду максимально эффективно
- Не ограничен искусственной 50%-й границей
- В больших графах с малым M — критически важно

**Минусы:**
- Требует постоянного пересчёта BFS для дистанции до дома
- Небольшой оверхед по производительности

**Когда хуже:** Практически никогда — это строго лучше алгоритма Алисы при любом M.

## Улучшение 3: Сбор нескольких ресурсов в комнате при наличии запаса еды

**Проблема исходного алгоритма:**  
В фазе исследования бот собирает только один (лучший) ресурс в каждой комнате, даже если у него есть запас еды.

**Предложение:**  
Если после сбора первого ресурса у бота достаточно еды для возврата домой — собрать и второй ресурс (и третий, и т.д.), оплачивая каждый следующий 1 едой.

```cpp
while (can_afford_collect_and_return()) {
    collectNext();
}
```

**Плюсы:**
- Бесплатный первый сбор уже используется правильно
- Дополнительные ресурсы "покупаются" дёшево (1 еда = 1 ресурс)
- Особенно выгодно в комнатах с несколькими ценными ресурсами

**Минусы:**
- Тратит еду раньше → меньше комнат в фазе исследования
- Плохо работает если gems и gold одновременно в одной комнате, но до следующей комнаты с gems надо 1 шаг: лучше пойти туда

**Когда хуже:** Когда каждая непосещённая комната содержит больше ценности, чем оставшиеся ресурсы в текущей.

## Улучшение 4: Оптимальный маршрут возврата через ценные комнаты

**Проблема исходного алгоритма:**  
На обратном пути бот идёт кратчайшим путём и собирает ресурсы только если есть излишки еды. Он не рассматривает небольшой крюк через богатую комнату.

**Предложение:**  
Перед возвратом рассчитать все пути домой с учётом возможных отклонений. Если обход через непосещённую комнату добавляет 2 шага, но даёт +46 ценности (gems) — это выгодно.

Это задача о нахождении пути с максимальной ценностью при ограничении на длину. Решается через модифицированный Дейкстра/BFS с состоянием `(текущая_комната, осталось_еды)`.

**Плюсы:**
- Кардинальное улучшение при неравномерном графе
- Может кратно увеличить итоговую ценность

**Минусы:**
- Значительно сложнее в реализации
- Экспоненциальная сложность в худшем случае (NP-hard при N→∞)
- Для N≤255 практично с мемоизацией

**Когда хуже:** Практически не бывает хуже — добавляет опциональность, а не ограничение.

---

## Улучшение 5: Учёт симметрии графа при исследовании

**Проблема исходного алгоритма:**  
Бот может "пинг-понгить" — идти 0→1→3→1→3, повторно проходя через уже посещённые комнаты для добирания до новых. Каждый проход тратит еду впустую.

**Предложение:**  
При выборе следующей непосещённой комнаты учитывать не только номер, но и топологию: выбирать комнату, минимизирующую суммарный путь с учётом последующих целей (жадный TSP-подход).

**Плюсы:**
- Снижает накладные расходы на перемещение
- Особенно важно при линейных графах (0-1-2-3-4-5...)

**Минусы:**
- Сложность O(N²) на шаг вместо O(N log N)
- При случайных графах выигрыш незначителен

## Сводная таблица

| Улучшение | Сложность реализации | Ожидаемый прирост | Риск ухудшения |
|---|---|---|---|
| Жадный выбор по ценности | Средняя | Высокий | Низкий |
| Динамический бюджет | Низкая | Высокий | Минимальный |
| Многократный сбор в комнате | Низкая | Средний | Средний |
| Оптимальный маршрут возврата | Высокая | Очень высокий | Нет |
| Учёт топологии маршрута | Высокая | Средний | Нет |

**Рекомендация:** Начать с улучшений 2 и 3 — они просты в реализации, не ухудшают поведение и дают измеримый прирост. Улучшение 4 — наиболее перспективное для максимизации ценности, но требует серьёзной реализации.
